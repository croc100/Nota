# 검증용 자료

0단계 알고리즘 검증(`docs/ALGORITHM.md` 8절)에 필요한 자료를 여기에 둔다.
**이 디렉토리의 실제 파일은 git에 커밋하지 않는다** — 악보와 녹음은 저작권이
있고 용량이 크다.

## 필요한 것

**악보 PDF 한 부와, 그 악보를 연주한 녹음 하나.** 실제로 연주하는 그대로면 된다.

이것이 기준이다. 메트로놈에 맞춘 연주, 페달 없는 연주, MIDI 동시 녹음, 손으로
적은 정렬 기준점 — 전부 진단에는 편하지만 **사용자가 실제로 겪는 상황이 아니다.**
실사용 조건에서 동작하지 않으면 통제된 조건에서 동작해도 의미가 없다.

따라서 요청은 단순하다.

- 악보 PDF (연주한 것과 같은 판본, 반복 처리도 동일하게)
- 그 악보를 연주한 녹음

페달을 쓰든, 루바토가 있든, 중간에 멈추든, 방이 울리든 그대로가 좋다. 그것이
제품이 마주할 조건이다.

### 한 가지 예외 — 압축

압축만은 다르다. **실제 앱은 마이크에서 raw PCM을 받지 파일을 읽지 않는다.**
저비트레이트 파일로 시험하면 제품에 존재하지 않는 열화를 측정하게 된다.

실측:

| 형식 | F | |
|---|---|---|
| WAV (어떤 표본화 주파수든) | 0.99 | 좋음 |
| MP3 320 / 192 kbps | 0.99 | 좋음 |
| Opus 128 kbps | 0.997 | 좋음 |
| MP3 128 kbps | 0.838 | 나쁨 |
| AAC 64 kbps 모노 (휴대폰 음성메모 기본값) | 0.775 | 매우 나쁨 |

표본화 주파수는 16 kHz까지 거의 영향이 없다(0.989). 온셋은 광대역 현상이고
저역이 충분히 싣는다. 문제는 비트레이트다 — 저비트레이트 코덱이 버리는 것이
정확히 트랜지언트이기 때문이다.

WAV나 MP3 320 kbps면 좋다. 여의치 않으면 그냥 보내도 된다. 다만 결과를 읽을
때 그 열화를 감안해야 하고, 그 열화는 실제 앱에는 없다.

AAC 수치는 ffmpeg 내장 인코더 기준이다. Apple 인코더는 더 낫다고 알려져 있으니
비관적일 수 있다.

### 정답 없이 잴 수 있는 것

라벨이 없어도 다음은 측정된다.

- **전체 드리프트.** 녹음의 시작과 끝이 곧 악보의 시작과 끝이므로 기준점 두 개가
  공짜로 생긴다. 끝났을 때 추적기가 악보 끝에 있는지로 누적 오차를 잴 수 있다.
  V6의 핵심이 이것이다.
- **템포 추정의 안정성.** 시간에 따른 추정 템포가 튀는지 본다.
- **어디서 깨지는지.** 위치 추적 궤적이 멈추거나 뛰는 지점이 그대로 보인다.
- **스크롤이 따라가는가.** 오디오 시간축에 맞춘 필름스트립으로 눈으로 확인한다.

정밀한 F-measure(V3, V4)는 온셋 라벨이 있어야 한다. 디지털 피아노로 오디오와
MIDI를 동시에 녹음할 기회가 생기면 그때 라벨이 공짜로 따라오지만, **먼저 할 일은
아니다.**
