# Nota 설계 문서

## 1. 제품 정의

피아노 연주자가 악보를 보며 연주하는 동안, 손을 쓰지 않고 악보가 알아서 진행되게 한다.

구현 범위는 두 층으로 나뉜다.

**기반 층 — 일반 악보 앱이 하는 것**
- PDF / 이미지 임포트, 악보 라이브러리, 폴더·태그 분류
- 뷰어: 확대, 회전, 양면/단면, 여백 잘라내기
- 스타일러스 필기 주석, 지우기, 레이어 분리
- 세트리스트, 메트로놈, 조표/박자 메모

**Nota 층 — 차별 기능**
- 이어붙인 악보의 자동 스크롤, 연주 오디오에 동기화

기반 층은 잘 알려진 영역이고 리스크가 없다. 이 문서는 Nota 층에 집중한다.

## 2. 핵심 UX 결정

### 2.1 연속 스크롤, 페이지 넘김 아님

PDF의 모든 페이지를 세로로 이어붙여 하나의 긴 캔버스를 만든다. 이 캔버스가 연주
속도에 비례해 위로 흘러간다.

페이지 넘김을 버린 이유:
- 넘김은 이산적 사건이므로 타이밍 오차가 그대로 실패로 드러난다. 한 박 늦으면
  연주자는 이미 지나간 마디를 보고 있다.
- 연속 스크롤은 오차가 "조금 위/아래로 어긋남"으로 나타나고, 악보는 여전히 화면에
  있다. 연주자가 복구할 수 있다.

### 2.2 읽기 선 (read line)

현재 연주 중인 위치를 화면 높이의 **약 1/3 지점**에 고정한다. 아래쪽 2/3는 앞으로
연주할 부분이므로 연주자는 항상 미리 읽을 수 있다. 이 지점은 사용자 조절 가능해야
한다 (초견 연주자는 더 위로, 암보에 가까운 연주자는 더 아래로 선호).

### 2.3 연주가 멈추면 스크롤도 멈춘다

이게 신뢰의 핵심이다. 연주자가 한 구절을 반복 연습하거나, 멈추고 생각하거나,
전화를 받을 때 악보가 계속 흘러가면 앱을 쓸 수 없다. 무음 감지 시 즉시 스크롤을
정지하고, 연주 재개 시 이어간다.

### 2.4 수동 개입이 항상 우선

사용자가 손으로 스크롤하면 자동 추적은 즉시 양보하고, 손을 뗀 위치를 새로운 현재
위치로 받아들인다. 자동 기능이 사용자와 싸우면 안 된다.

## 3. 대상 플랫폼

iOS와 Android 양쪽을 만든다.

### 3.1 우선순위 — iOS/iPadOS 먼저

동시 출시하지 않는다. iOS를 먼저 완성하고 Android가 따라간다. 근거:

- **시장 현실**: 악보 앱의 주 사용 기기는 태블릿이고, 그중에서도 iPad가 지배적이다
  (forScore, Piascore 등 기존 강자들이 iPad 중심). 10인치 이상 화면이 아니면
  악보 한 시스템을 읽을 만하게 띄우기 어렵다.
- **변수 통제**: 0단계에서 검증할 알고리즘은 마이크 특성과 오디오 레이턴시에
  민감하다. 하드웨어가 균일한 iOS에서 먼저 알고리즘을 확정하고, 그 다음
  Android의 하드웨어 편차에 대응하는 것이 순서상 맞다. 반대로 하면 알고리즘
  문제와 기기 문제를 구분할 수 없다.
- **필기 주석**: PencilKit이 저지연 잉킹을 공짜로 제공한다. Android에는 동급의
  기성품이 없다(`androidx.ink`가 있으나 더 손이 간다).

### 3.2 그러나 코어는 1일차부터 크로스 플랫폼

우선순위가 iOS라는 것이 "일단 iOS로 만들고 나중에 이식한다"는 뜻은 **아니다.**
나중에 이식하는 선택은 거의 항상 코어 재작성으로 귀결된다.

공유 코어는 첫 커밋부터 플랫폼 중립으로 작성한다. 코어 코드에 Apple API,
Foundation 타입, iOS 가정이 단 하나도 들어가지 않는다. 이 규칙은 CI에서
**Linux 빌드를 통과시키는 것으로 강제**한다 (9.3절).

### 3.3 최소 지원 버전

| 플랫폼 | 최소 | 비고 |
|---|---|---|
| iOS / iPadOS | 17.0 | Swift C++ interop, 최신 PDFKit |
| Android | API 29 (Android 10) | AAudio 성숙, scoped storage |

## 5. 모듈

### 5.1 공유 — NotaCore (C++)

| 모듈 | 책임 |
|---|---|
| `nota::RingBuffer` | lock-free SPSC 링 버퍼. 오디오 콜백 전용 |
| `nota::AudioFollower` | STFT, 온셋 검출, 템포 추정, 무음 판정 |
| `nota::ScoreGeometry` | 악보 비트맵 → 오선·시스템·마디선 → 시간↔픽셀 매핑 |
| `nota::ScoreRaster` | PDFium 기반 페이지 래스터화, 타일 캐시 |
| `nota::PositionEstimator` | 오디오 신호 → 악보상 위치, 재동기화 |
| `nota::ScrollController` | 위치 → 부드러운 화면 오프셋 |
| `nota::ScoreDocument` | 악보 메타데이터, 캔버스 좌표계, 직렬화 |

**원칙**: 이 안에는 플랫폼 API가 없다. 입력은 PCM 버퍼와 비트맵, 출력은 숫자다.
파일 I/O조차 호출자가 주입한 인터페이스로 처리한다.

### 5.4 공유하지 않는 이유 — UI와 잉킹

UI는 두 번 작성한다. 의도된 선택이다.

이 앱의 뷰어는 평범한 폼 화면이 아니다. 거대한 캔버스를 60~120 Hz로 끊김 없이
스크롤하면서, 스타일러스 입력에 수 밀리초 단위로 반응해야 한다. 크로스 플랫폼 UI
프레임워크가 가장 약한 지점이 정확히 이 둘이다(8.3절).

잉킹은 특히 플랫폼 기성품이 압도적으로 낫다. PencilKit은 예측 터치와 하드웨어
가속을 공짜로 준다. 이것을 공유 코드로 재구현하면 iOS 품질이 하락한다.

대신 **가장 복잡하고 위험한 부분은 전부 코어에 있다.** UI는 코어가 계산한 오프셋을
그리는 얇은 층이다.

## 6. 핵심 문제 A — 시간을 픽셀로 바꾸는 것

오디오에서 "4마디 진행했다"를 알아내도, **그게 캔버스에서 몇 픽셀인지** 모르면
스크롤할 수 없다. 이 매핑이 Nota의 중심 문제다.

악보는 균일하지 않다. 어떤 시스템(줄)에는 2마디, 어떤 줄에는 6마디가 들어간다.
따라서 "초당 N픽셀" 같은 고정 속도는 금방 틀어진다.

### 접근: 가벼운 CV로 악보 구조만 추출 (OMR 아님)

음표를 인식하는 건 어렵지만, **악보의 구조**를 찾는 건 훨씬 쉽고 안정적이다.

1. **오선 검출** — 수평 투영 프로파일. 오선은 페이지 폭 전체에 걸친 검은 수평선
   이므로 투영값에서 5개씩 묶인 뚜렷한 피크로 나타난다. 고전적이고 신뢰성 높은 기법.
2. **시스템 그룹화** — 피아노 악보는 대보표(grand staff)이므로 오선 묶음이 2개씩
   짝지어진다. 좌측의 중괄호(brace)와 오선 간격으로 짝을 판정한다.
3. **마디선 검출** — 각 시스템 내부에서 수직 투영. 마디선은 대보표 상하를 관통하는
   수직선이다.
4. **결과** — `[(마디 번호, y 범위)]` 테이블. 즉 마디 단위의 시간↔픽셀 매핑.

박자표(4/4 등)를 알면 마디 → 박 변환이 되고, 매핑이 완성된다. 박자표는 사용자가
지정하거나 첫 시스템에서 간단히 인식한다.

상세는 `docs/ALGORITHM.md` 5절.

### 매핑 정밀도 등급

| 등급 | 입력 | 정밀도 | 비고 |
|---|---|---|---|
| A | MusicXML / MIDI 동반 | 음표 단위 | 가장 정확. 지원 악보 한정 |
| B | PDF + 오선·마디선 CV | 마디 단위 | **기본 경로.** 대부분의 악보에서 동작 |
| C | 사용자 캘리브레이션 | 사용자 지정 지점 | B 실패 시 폴백. 한 번 훑으며 탭 |

B가 기본이고, A는 있으면 쓰고, C는 안전망이다.

## 7. 핵심 문제 B — 드리프트

템포를 추정해서 적분하면 위치가 나오지만, **오차가 누적된다.** 템포 추정이 1%
틀리면 3분 연주 후 약 1.8초, 템포 120에서 3~4박 어긋난다. 한 시스템 가까이 벗어난다.

게다가 실제 연주에는 루바토, 페르마타, 리타르단도, 반복, 도돌이, 즉흥적 멈춤이 있다.
순수 적분은 이것들을 전부 틀린다.

### 완화 전략

1. **절대 위치 재동기화** — 적분만 믿지 않는다. 주기적으로 독립적인 위치 추정을
   수행해 보정한다. 수단:
   - 등급 A: 크로마 특징을 악보 음표와 매칭 (온라인 DTW)
   - 등급 B: 시스템별 **음표 밀도**를 CV로 추정(잉크 밀도가 음표 수의 좋은 근사)하고,
     실제 온셋 밀도와 비교해 위치를 추정
2. **정지 감지** — RMS가 임계 이하로 지속되면 적분을 멈춘다. 재개 시 이어감.
   드리프트 누적의 가장 큰 원인(연주 안 하는 동안의 전진)을 제거한다.
3. **속도 제한** — 추정 템포가 급변해도 스크롤 속도 변화율에 상한을 둔다. 오추정이
   화면을 날려버리지 않게 한다.
4. **사용자 보정** — 손 스크롤로 언제든 재동기화. 2.4절 참조.
5. **반복 구간 수동 지정** — 도돌이표/세뇨는 자동 추적이 매우 어렵다. 사용자가
   미리 반복 횟수를 지정하거나, 반복 구간에서는 추적을 느슨하게 한다.

드리프트를 완전히 없애는 건 목표가 아니다. **연주자가 읽을 수 있는 범위 안에
유지하는 것**이 목표다. 읽기 선이 화면 1/3에 있으므로 위아래로 상당한 여유가 있다.

## 8. 기술 스택 결정

### 8.1 공유 코어는 C++17

`NotaCore`를 C++17로 작성한다. 근거는 네 가지다.

**(1) 코어는 반드시 공유되어야 한다.**
온셋 검출, 템포 추정, 오선 검출, 위치 추정, 스크롤 제어는 이 프로젝트에서 가장
어렵고 가장 위험한 코드다. 이것을 Swift와 Kotlin으로 두 번 작성하면 작업량이
두 배가 되는 것으로 끝나지 않는다. 두 구현이 **미묘하게 다르게 동작**하기 시작하고,
"iOS에서는 되는데 Android에서는 드리프트가 생긴다"는 디버깅 불가능한 상황이 된다.
신호 처리 코드는 파라미터 하나로 거동이 바뀌므로 특히 그렇다.

**(2) C++은 양쪽에 마찰 없이 들어간다.**
- Android: NDK가 C++을 1급으로 지원한다. CMake를 Gradle이 직접 빌드한다.
- iOS: Swift 5.9+의 C++ interop으로 브릿지 코드 없이 직접 호출된다.
- SIMD: NEON/vDSP 양쪽에 접근 가능하다. DSP 핫 루프에서 중요하다.

**(3) 필요한 라이브러리가 C++이다.**
- **PDFium** — 양 플랫폼에서 동일한 PDF 래스터 결과를 얻는 현실적 수단. Android의
  기본 `PdfRenderer`는 기능과 성능이 제한적이라 어차피 PDFium으로 간다. PDFium은
  C++이다. 래스터와 기하 분석이 같은 언어에 있는 것이 자연스럽다.
- **Oboe** — Android 저지연 오디오의 사실상 표준. C++ 라이브러리다.

이 두 의존성이 Rust 대신 C++을 택한 결정적 요인이다.

**(4) 이 저장소가 Linux CI에서 코어를 빌드·테스트할 수 있다.**
Xcode도 Android Studio도 없이 코어의 단위 테스트와 알고리즘 검증을 돌릴 수 있다.
이는 개발 속도에 직접 영향을 준다. 9.3절 참조.

### 8.2 번복된 결정 — 기록

이 저장소의 첫 커밋(`469d1ff`)은 **Swift 중심 + C 링 버퍼만** 구조를 채택했고,
C++ 코어를 "과설계"로 명시적으로 기각했다.

그 판단의 근거는 "iOS 전용이 명시된 목표이므로 이식성을 수용 가능한 손실로 본다"
였다. Android가 요구사항에 추가되면서 **그 전제가 소멸**했고, 따라서 결정을
뒤집는다.

이전 논리 자체가 틀렸던 것은 아니다. iOS 전용이라면 여전히 Swift 중심이 옳다.
전제가 바뀌었으므로 결론이 바뀐 것이다. 전체 맥락은
`docs/decisions/0001-core-language.md`에 기록한다.

### 8.3 기각한 대안

| 대안 | 기각 이유 |
|---|---|
| **Rust 코어** | 가장 근접한 후보였다. 메모리 안전성과 테스트 도구는 C++보다 우수하다. 그러나 PDFium과 Oboe가 모두 C++이라 양쪽 모두 바인딩 작업이 추가되고, Swift·Kotlin 양쪽에 FFI 계층(UniFFI/cbindgen + JNI)이 또 필요하다. 계층 수가 늘어나는 비용이 안전성 이득을 상쇄한다고 판단했다. |
| **Kotlin Multiplatform** | 비즈니스 로직 공유에는 훌륭하지만 실시간 DSP에는 부적합하다. Kotlin/Native의 런타임과 메모리 관리가 오디오 콜백에 들어가면 예측 불가능하고, SIMD 인트린직 접근 경로가 없다. |
| **Flutter** | 이 앱은 본질적으로 "고성능 커스텀 캔버스 + 실시간 오디오"다. Dart는 DSP를 못 하므로 어차피 C++ FFI가 필요하고, 그러면 Flutter의 이점은 UI뿐이다. 그런데 저지연 스타일러스 잉킹과 거대 캔버스 스크롤이 Flutter의 약점이다. 이점만 없고 약점만 겹친다. |
| **Compose Multiplatform** | iOS 타깃 성숙도가 아직 부족하고, 잉킹·PDF 생태계가 약하다. |
| **React Native** | 위 문제가 더 심하다. |

### 8.4 UI는 각 플랫폼 네이티브

- iOS: Swift + SwiftUI + PencilKit
- Android: Kotlin + Jetpack Compose + `androidx.ink`

근거는 5.4절.

### 8.5 왜 서버가 아닌 온디바이스인가

- 레이턴시: 스크롤은 수십 ms 단위로 반응해야 한다. 왕복 네트워크는 불가능하다.
- 프라이버시: 마이크 스트림을 서버로 보내는 앱은 신뢰받기 어렵고 심사도 까다롭다.
- 오프라인: 연습실·무대에 네트워크가 없을 수 있다.

전부 온디바이스로 처리한다.

## 9. 빌드와 검증

### 9.1 저장소 구조

```
Nota/
├── core/                  NotaCore — 공유 C++
│   ├── CMakeLists.txt
│   ├── include/nota/
│   ├── src/
│   └── tests/             GoogleTest 단위 테스트
├── tools/                 CLI 검증 하네스 (9.3절)
├── ios/                   Xcode 프로젝트, Swift 코드
├── android/               Gradle 프로젝트, Kotlin 코드
├── prototype/             알고리즘 탐색 (Python 플로팅·지표)
└── docs/
```

### 9.2 빌드 체계

코어는 **CMake** 하나로 관리하고, 각 플랫폼이 이를 소비한다.

| 타깃 | 방식 |
|---|---|
| Android | Gradle `externalNativeBuild`가 CMake를 직접 호출 |
| iOS | CMake → XCFramework 생성 → Xcode가 링크 |
| Linux (CI/개발) | CMake → 정적 라이브러리 + 테스트 + CLI 도구 |

### 9.3 Linux에서 코어를 검증한다

C++ 코어 선택의 실질적 이점이다. 코어가 플랫폼 중립이므로 **Xcode나 Android
Studio 없이도** 다음이 가능하다.

- 코어 단위 테스트 전체 실행
- 알고리즘 검증(10절 V1~V7)을 실제 악보 PDF와 오디오 파일로 실행
- CI에서 매 커밋 검증

CLI 하네스를 둔다:

```
nota-analyze  score.pdf          → 검출된 시스템·마디 좌표를 JSON으로 출력
nota-follow   audio.wav  geom.json → 시간에 따른 추정 위치 추적을 CSV로 출력
nota-onsets   audio.wav          → 온셋 시각 목록 출력
```

이 도구들은 **프로덕션 코어를 그대로 호출**한다. 별도 프로토타입 구현이 아니므로
검증한 것과 배포하는 것이 같은 코드다.

`prototype/`의 Python은 알고리즘을 다시 구현하지 않는다. 위 CLI 출력을 받아
**시각화와 지표 계산만** 한다 (검출된 오선을 이미지에 겹쳐 그리기, ODF 곡선 플롯,
F-measure 계산). 탐색 속도는 Python에서, 구현은 C++에서.

또한 이 규칙이 3.2절의 "코어에 플랫폼 코드 금지"를 자동으로 강제한다. Apple API가
섞이면 Linux 빌드가 깨진다.

|---|---|---|
| 오선/마디선 CV가 다양한 악보에서 실패 | 높음 | 실제 PDF 표본으로 조기 검증(V1, V2). 등급 C 폴백 |

| **Android 오디오 레이턴시·하드웨어 편차** | 높음 | Oboe 사용. 저가 기기 실측 후 최소 사양 재설정 |
| 피아노 울림·페달로 온셋 검출 저하 | 중간 | 스펙트럼 화이트닝 + 적응 임계. 실측 필요(V4) |
| 환경 소음 / 다른 악기 | 중간 | 피아노 전용 가정, 대역 제한 |
| 반복·도돌이 구간 추적 실패 | 중간 | 수동 지정 |
| 배터리 소모 (상시 마이크 + 렌더) | 중간 | 프레임 레이트 적응, 측정 후 최적화 |
| UI를 두 번 작성하는 비용 | 중간 | 수용된 선택(5.4절). 복잡도는 코어에 격리 |
| PDFium 통합·바이너리 크기 | 낮음 | 필요한 모듈만 빌드 |

## 11. 로드맵

**0단계 — 알고리즘 검증 (Xcode·Android Studio 불필요)**
`core/` + `tools/`를 Linux에서 빌드해 실제 악보와 녹음으로 V1~V7을 검증한다.
이 단계가 실패하면 제품이 성립하지 않으므로 가장 먼저 한다.

**1단계 — iOS 기반 악보 앱**
임포트, 라이브러리, 이어붙인 연속 스크롤 뷰어(수동), PencilKit 주석.
Nota 기능 없이도 쓸 만한 악보 앱이 되어야 한다.

**2단계 — iOS 자동 스크롤**
코어를 XCFramework로 연결. 정지 감지, 속도 제한, 수동 개입 양보 포함.
여기서 제품 가설을 실사용으로 검증한다.

**3단계 — Android 이식**
코어는 그대로 재사용. Compose UI, Oboe 캡처, `androidx.ink` 주석을 작성한다.
기기별 마이크 전처리 대응이 이 단계의 주 작업이다.

**4단계 — 정밀도 향상 (양 플랫폼)**
재동기화 고도화, 등급 A(MusicXML/MIDI), 등급 C(캘리브레이션), 반복 구간 처리.

**5단계 — 완성도**
세트리스트, 메트로놈, 태블릿 레이아웃 최적화, 접근성.
