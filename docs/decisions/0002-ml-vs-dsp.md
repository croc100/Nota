# 0002. 어디에 ML을 쓸 것인가

- 상태: 채택
- 날짜: 2026-11-05

## 맥락

"CV 임계값을 손으로 맞추는 대신 ML을 쓰면 빨리 끝나지 않는가"라는 질문이
나왔다. 타당한 물음이다. 추측 대신 실제로 돌려보고 비용을 쟀다.

## 측정

### ML OMR (oemer, ONNX)

악보 이미지에서 바로 음표 데이터를 뽑는다. 성공하면 등급 A가 되어 드리프트
문제 자체가 사라지므로, 가장 큰 지렛대다.

| 항목 | 실측 |
|---|---|
| 모델 크기 | **209 MB** (UNet 68 MB + segnet 37 MB 등 4개) |
| 1페이지 처리 | **약 4분** (서버 CPU, ONNX Runtime) |
| 실행 가능 여부 | 버전 고정 필요 — numpy < 2, onnxruntime 1.20 |

Python 3.13 + numpy 2.x 환경에서는 추론 단계까지는 통과했으나 후처리에서
멈췄다. 되게 하려면 의존성을 과거 버전에 묶어야 한다.

### 현재 CV 경로

| 항목 | 실측 |
|---|---|
| 정확도 | 실제 악보 5페이지 V1/V2 **F = 1.000** |
| 처리 시간 | 1페이지 1초 미만 |
| 모델 크기 | 0 |
| 외부 의존성 | 없음 |
| 레이아웃 내성 | 오선 간격 8~36 px, 위치 불변, 종횡비 ±25%, 잘림 내성 |
| 열화 내성 | 기울기 3°, 잡음 σ20, 음영 0.8, JPEG q30 |

### 온셋 검출 (합성 오디오)

`prototype/evaluate_onsets.py`. MIDI에서 정답이 그대로 나오므로 라벨링이 없다.

| 조건 | 스펙트럴 플럭스 (설계안) | librosa |
|---|---|---|
| 페달 없음 | 0.989 | 0.999 |
| 페달 최대 | 0.990 | 0.999 |
| + 성당 잔향 3s | 0.971 | 0.999 |
| 어택 트랜지언트 제거 | 0.989 | 0.999 |

## 결정

**CV(악보 분석)에는 ML을 쓰지 않는다. 오디오 쪽은 실제 녹음을 받은 뒤에
판단한다.**

## 근거

### CV에 ML을 쓰지 않는 이유

이미 F = 1.000이다. 209 MB와 페이지당 4분을 지불해 1.000을 1.000으로 바꾸는
거래다. 앱 번들 크기와 임포트 대기 시간은 사용자가 바로 체감하는 비용이다.

손으로 맞춘 임계값이 많다는 지적은 맞다. 다만 그 값들은 추측이 아니라 전부
실측에서 나왔고, 평탄 구간을 찾아 중앙을 택했으며, 근거가 주석과 문서에
남아 있다. 표본이 늘어 깨지면 재측정으로 고칠 수 있고, 무엇이 왜 틀렸는지
알 수 있다. 학습된 모델은 그 자리에서 "왜"를 알려주지 않는다.

ML을 재검토할 조건: 표본을 넓혔을 때(특히 실제 스캔본, 필사본, 복잡한 현대
기보) 현재 방식이 무너지고 임계 조정으로 회복되지 않는 경우.

### 오디오를 아직 판단하지 않는 이유

합성 오디오로는 **판정이 불가능하다는 것이 측정으로 드러났다.** 페달을 끝까지
밟아도, 어택 트랜지언트를 0으로 지워도, 성당 잔향을 걸어도 검출기가 F ≈ 0.99를
유지한다. 가산 합성은 음이 시작될 때 배음열을 통째로 더하므로 수학적으로
날카로운 스펙트럼 불연속을 만들고, 그것이 어떤 열화에도 살아남기 때문이다.

실제 피아노를 어렵게 만드는 요소 — 현의 공명, 복잡한 어택, 마이크 응답, 기기
전처리 — 는 재현되지 않는다. 따라서 **V3/V4는 실제 녹음 없이는 답이 없다.**
이것은 가정이 아니라 측정된 결론이다.

다만 얻은 것이 있다.

- 설계한 스펙트럴 플럭스 구현이 명세대로 동작한다. 온셋이 있으면 찾는다.
- librosa가 일관되게 1% 가량 앞서고, 잔향에서는 격차가 커진다(0.971 대 0.999).
  차이는 주로 피크 선택과 멜 대역 정규화에서 온다. 실제 녹음 전에도 개선 여지가
  어디인지는 알 수 있다.
- 녹음이 도착하면 같은 채점기를 그대로 쓴다. 정답만 MIDI에서 사람이 라벨한
  것으로 바꾸면 된다.

## 결과

**긍정적**
- 앱 번들에 모델이 들어가지 않는다
- 임포트가 즉시 끝난다
- 검출이 틀렸을 때 원인을 추적할 수 있다
- ONNX Runtime이 C++에서 iOS/Android 모두 동작함은 확인했으므로, 나중에 필요해
  지면 경로는 열려 있다

**부정적**
- 손으로 맞춘 임계값이 여럿 남는다. 표본이 넓어지면 재측정이 필요하다
- 등급 A(음표 단위)는 MusicXML/MIDI가 동반된 악보에서만 가능하다. ML OMR로
  모든 PDF에서 등급 A를 얻는 길은 지금 택하지 않았다
