# 0001. 공유 코어의 언어

- 상태: 채택
- 날짜: 2026-11-04
- 이전 결정 번복: 초기 커밋 `469d1ff`의 "Swift 중심 + C 링 버퍼" 구조

## 맥락

Nota의 핵심 기능은 마이크로 들은 피아노 연주에 맞춰 이어붙인 악보를 자동
스크롤하는 것이다. 이를 위해 필요한 코드는 다음과 같다.

- 실시간 오디오 캡처와 lock-free 링 버퍼
- STFT, 스펙트럼 플럭스 온셋 검출, 적응 임계 피크 선택
- 콤 필터 기반 템포 추정과 옥타브 오류 처리
- 악보 이미지의 오선·대보표·마디선 검출 (투영 프로파일 기반 CV)
- 박자 적분 + 온셋 밀도 매칭 기반 위치 추정
- 임계 감쇠 스프링 스크롤 제어

이것이 이 프로젝트에서 가장 어렵고 가장 위험한 코드다.

요구 플랫폼이 **iOS 전용에서 iOS + Android로 변경**되었다. 이 결정은 그 변경에
대한 응답이다.

## 이전 결정과 그 전제

초기 설계는 Swift 중심 구조를 채택했다. 논리는 다음과 같았다.

> 실시간 제약(데드라인 미스 = 오디오 드롭아웃)이 걸리는 것은 오디오 입력 탭
> 콜백 한 곳뿐이고, 거기서 하는 일은 PCM 샘플을 링 버퍼에 복사하는 것뿐이다.
> 이는 할당도 락도 없는 20여 줄의 C로 끝난다. STFT·온셋·템포 추정은 모두 콜백
> 밖 워커 스레드에서 수행되므로 ARC의 비결정성이 문제되지 않는다. 따라서
> Swift + Accelerate로 충분하다.
>
> 얻는 것: 단일 언어 코드베이스, 브릿지 불필요, 빠른 반복 개발.
> **포기하는 것: 엔진의 타 플랫폼 이식성. iOS 전용이 명시된 목표이므로 수용한다.**

이 논리는 그 전제 아래에서 타당했다. 실시간 제약의 범위를 정확히 좁게 본 것도
옳았다. 그러나 명시적으로 교환 대상으로 삼은 것이 바로 **이식성**이었고, 이제
그것이 요구사항이 되었다. 전제가 소멸했으므로 결론을 유지할 수 없다.

## 결정

공유 코어 `NotaCore`를 **C++17**로 작성한다. UI는 각 플랫폼 네이티브로 둔다
(Swift/SwiftUI, Kotlin/Compose).

## 근거

### 1. 코어는 두 번 작성할 수 없다

Swift와 Kotlin으로 각각 구현하면 작업량이 두 배가 되는 것으로 끝나지 않는다.
신호 처리 코드는 파라미터와 수치 처리 순서 하나로 거동이 달라진다. 두 구현은
반드시 미묘하게 어긋나기 시작하고, 결국 "iOS에서는 드리프트가 없는데 Android에서는
생긴다"는, 어느 쪽이 맞는지조차 알 수 없는 디버깅 상황에 도달한다.

알고리즘은 하나여야 한다. 검증한 것과 배포하는 것이 같은 코드여야 한다.

### 2. C++은 양쪽에 마찰 없이 들어간다

- Android: NDK가 C++을 1급으로 지원하고, Gradle이 CMake를 직접 빌드한다.
- iOS: Swift 5.9+의 C++ interop으로 Objective-C++ 브릿지 없이 직접 호출된다.
- SIMD: NEON 인트린직에 직접 접근할 수 있다. DSP 핫 루프에서 유효하다.

### 3. 필요한 의존성이 이미 C++이다

이것이 Rust 대신 C++을 택한 결정적 요인이다.

- **PDFium** — 두 플랫폼에서 동일한 PDF 래스터 결과를 얻기 위해 필요하다.
  Android 기본 `PdfRenderer`는 기능·성능이 제한적이므로 어차피 PDFium으로 간다.
  래스터화와 악보 기하 분석이 같은 언어에 있는 것이 자연스럽다.
- **Oboe** — Android 저지연 오디오의 사실상 표준이며 C++ 라이브러리다.

Rust를 택하면 이 둘에 대한 바인딩을 만들고 유지해야 하고, 그 위에 Swift용
FFI(UniFFI 또는 cbindgen)와 Kotlin용 JNI 계층이 각각 더 얹힌다. 계층이 늘어나는
비용이 메모리 안전성 이득을 상쇄한다고 판단했다.

### 4. Xcode 없이 코어를 검증할 수 있다

코어가 플랫폼 중립 C++이면 Linux에서 빌드·테스트된다. 단위 테스트와 알고리즘
검증(V1~V7)을 Xcode나 Android Studio 없이 CI에서 매 커밋 돌릴 수 있다.

부수 효과로, 이 규칙이 "코어에 플랫폼 코드 금지"를 **자동으로 강제**한다.
Apple API가 섞이면 Linux 빌드가 깨지므로 CI가 즉시 잡아낸다.

## 기각한 대안

### Rust

가장 근접한 후보였다. 메모리 안전성, 테스트 도구, 의존성 관리 모두 C++보다 우수
하다. 실시간 코드에서도 할당을 피하면 충분히 안전하다.

기각 이유는 근거 3이다. PDFium과 Oboe가 모두 C++이고, 그 위에 Swift와 Kotlin
양쪽 FFI가 더 필요하다. 접착 계층의 총량이 C++ 선택보다 분명히 많다.

재검토 조건: PDF 래스터화를 순수 Rust 크레이트로 대체할 수 있다고 판단되거나,
오디오 캡처를 각 플랫폼 네이티브 코드로 올리고 코어는 순수 계산만 담당하도록
경계를 다시 그을 경우.

### Kotlin Multiplatform

비즈니스 로직 공유에는 훌륭한 선택이지만 실시간 DSP에는 맞지 않는다.
Kotlin/Native의 런타임과 메모리 관리가 오디오 처리 경로에 들어가면 지연이
예측 불가능해지고, SIMD 인트린직 접근 경로가 없다.

### Flutter

이 앱은 본질적으로 "고성능 커스텀 캔버스 + 실시간 오디오"다. Dart로 DSP를 할 수
없으므로 어차피 C++ FFI가 필요하고, 그러면 Flutter가 주는 이점은 UI 공유뿐이다.
그런데 저지연 스타일러스 잉킹과 거대 캔버스의 끊김 없는 스크롤이 정확히 Flutter의
약점이다. 이점은 겹치지 않고 약점만 겹친다.

### Compose Multiplatform / React Native

iOS 타깃 성숙도, 잉킹 생태계, PDF 렌더 성능에서 같은 문제가 더 크게 나타난다.

## 결과

**긍정적**
- 알고리즘 구현이 하나로 유지된다
- Linux CI에서 코어 전체를 검증할 수 있다
- PDFium·Oboe를 바인딩 없이 직접 사용한다
- 플랫폼 코드 침입이 CI로 강제 차단된다

**부정적**
- UI를 두 번 작성한다 (의도된 교환. `DESIGN.md` 5.4절)
- C++의 메모리 안전성 부담을 진다 → 완화: 코어에 raw 포인터 산술 금지,
  `std::span`·RAII 사용, 산술 코드에 sanitizer(ASan/UBSan) CI 필수
- 빌드 체계가 셋이 된다 (CMake / Xcode+XCFramework / Gradle+NDK)
- iOS만 보면 Swift 단일 언어보다 복잡하다

## 메모

iOS 전용이 유지되었다면 이전 결정이 여전히 옳다. 이 번복은 판단 오류의 교정이
아니라 **전제 변경에 따른 재결정**이다. 향후 Android 요구가 철회되는 일이
생긴다면 이 문서를 다시 열어야 한다.
