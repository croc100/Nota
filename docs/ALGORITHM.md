# Nota 알고리즘 상세

이 문서는 `NotaCore`의 `AudioFollower`, `ScoreGeometry`,
`PositionEstimator`, `ScrollController` 네 모듈의 구체적 동작을 기술한다.
모두 플랫폼 중립 C++로 구현되며 iOS와 Android가 동일한 코드를 사용한다
(`docs/decisions/0001-core-language.md`).

아래 파라미터는 **설계 초기값**이며, 0단계 검증(실제 피아노 녹음과 악보 표본)에서
측정 후 조정한다. 근거 없이 확정된 값이 아니다.

---

## 1. 오디오 입력

### 1.1 캡처

캡처는 플랫폼 코드가 담당하고, 코어는 PCM 프레임만 받는다.

- 샘플레이트 44100 Hz, 모노
- 콜백 버퍼 512 프레임

**공통 요구사항 — 전처리를 반드시 끌 것.** 자동 게인 제어(AGC)와 노이즈 억제는
온셋 검출을 직접적으로 훼손한다. AGC는 셈여림을 평탄화해 에너지 상승을 지워버리고,
노이즈 억제는 타현음의 트랜지언트를 깎는다.

| 플랫폼 | API | 전처리 비활성화 |
|---|---|---|
| iOS | `AVAudioEngine` 입력 탭 | `AVAudioSession` 카테고리 `.record`, 모드 `.measurement` |
| Android | Oboe / AAudio | 오디오 소스 `UNPROCESSED` 요청 |

Android는 이것이 보장되지 않는다. `UNPROCESSED`는
`PROPERTY_SUPPORT_AUDIO_SOURCE_UNPROCESSED`가 `true`인 기기에서만 동작하고,
미지원 기기에서는 `VOICE_RECOGNITION`으로 폴백한다(`VOICE_COMMUNICATION`은
에코 제거와 AGC가 강하게 걸리므로 절대 쓰지 않는다). 그래도 전처리를 완전히
끌 수 없는 기기가 존재하므로, 기기별 실측과 적응 임계 조정이 필요하다.
`DESIGN.md` 10절의 Android 리스크 항목.

### 1.2 링 버퍼

오디오 콜백은 실시간 스레드에서 호출된다. 여기서 할당·락·가비지 컬렉션·ARC
리테인이 발생하면 데드라인을 놓치고 오디오가 끊긴다. 따라서 링 버퍼는 코어의
C++ 코드이며, 양 플랫폼의 콜백이 직접 여기에 쓴다.

단일 생산자 / 단일 소비자 구조이므로 락이 필요 없다.

용량은 2의 거듭제곱(`1 << 18` = 262144 프레임 ≈ 5.9초 @44.1kHz)으로 두어
모듈로를 마스킹으로 대체한다. 위치는 64비트 단조 증가 카운터로 추적한다.

**카운터가 둘인 이유.** 소박한 구현은 `write_index` 하나만 둔다. 그러면 틀린다.
생산자는 데이터를 memcpy한 **뒤에** `write_index`를 올리므로, 소비자가 보는
`write_index`가 `w`일 때 생산자는 이미 `[w, w+n)` 구간의 인덱스에 쓰고 있을 수
있다. 그 인덱스는 논리 위치 `[w-capacity, w+n-capacity)`와 같은 자리다. 즉
소비자가 가장 오래된 끝(`w-capacity` 부근)을 읽으면 생산자가 지금 덮어쓰는 중인
메모리를 읽는다. `write_index`는 아직 올라가지 않았으므로 **어떤 사후 검증으로도
이를 알아낼 수 없다.**

따라서 카운터를 둘로 나눈다.

| 카운터 | 갱신 시점 | 용도 |
|---|---|---|
| `reserved_pos` | memcpy **전** | 덮어쓰기 경계 — 소비자의 안전 하한 |
| `write_pos` | memcpy **후** | 읽어도 되는 데이터의 상한 |

- 생산자: `reserved_pos`를 release로 공개 → memcpy → `write_pos`를 release로 공개
- 소비자: `write_pos`를 acquire로 읽어 상한을, `reserved_pos`를 acquire로 읽어
  하한(`reserved_pos - capacity`)을 잡는다
- 복사 후 `reserved_pos`를 다시 확인해 구간이 침범당하지 않았는지 검증한다.
  침범당했으면 복사본을 버리고 재시도한다. 찢어진 PCM을 분석에 넣는 것보다
  빈손으로 돌아가는 편이 낫다
- 오버런(소비자가 뒤처짐) 시 가장 오래된 데이터를 버린다. 실시간 추적에서는
  과거 데이터보다 최신 데이터가 중요하다

두 카운터의 차이는 진행 중인 쓰기 한 번의 크기(콜백 512)이므로 실질 용량 손실은
무시할 수 있다.

> 이 설계는 구현 중 동시성 테스트가 실패하면서 발견했다. 처음에는 카운터 하나에
> 사후 검증만 두었고, 그것으로 충분하다고 판단했다. 스트레스 테스트에서 값이
> 정확히 `capacity - 1`만큼 역행하는 현상이 재현되어 원인을 추적한 결과가 위
> 내용이다. 단위 테스트 없이 넘어갔다면 기기에서 간헐적 온셋 오검출로 나타났을
> 것이고, 원인 규명은 훨씬 어려웠을 것이다.

워커 스레드 외의 모든 분석은 이 버퍼에서 읽어 수행한다.

## 2. 온셋 검출

피아노는 타현 악기이므로 음의 시작에 뚜렷한 에너지 상승이 있다. 이것이 박자 추적의
1차 재료다.

### 2.1 STFT

- 윈도우 2048 샘플 (≈46.4 ms), Hann
- 홉 512 샘플 (≈11.6 ms) → 분석 프레임 레이트 ≈86.1 Hz
- 대역 제한 50 Hz ~ 5000 Hz
  (피아노 기본주파수는 A0 27.5 Hz ~ C8 4186 Hz. 50 Hz 아래는 공조·발소리 등
  저역 소음이 지배하고, 5 kHz 위는 온셋 정보 대비 노이즈가 많다.)

### 2.2 온셋 검출 함수 (ODF)

스펙트럼 플럭스를 쓴다. 로그 압축을 먼저 적용해 큰 음량의 지배를 줄인다.

```
Y_n(k) = log(1 + γ · |X_n(k)|)          γ = 1000

ODF(n) = Σ_k max(0, Y_n(k) - Y_{n-1}(k))
```

양의 변화만 더하는 이유: 음이 시작될 때(에너지 증가)만 반응하고 감쇠에는 반응하지
않게 하기 위함이다.

**피아노 특유의 문제** — 서스테인 페달을 밟으면 이전 음들이 계속 울리는 상태에서
새 음이 추가되므로 상대적 에너지 변화가 작아진다. 대응:
- 스펙트럼 화이트닝(각 주파수 빈을 최근 최대값으로 정규화)을 ODF 계산 전에 적용
- 저역보다 중·고역에 가중치를 둔다 (페달 울림은 저역에 몰린다)

이 부분은 0단계에서 실측으로 검증해야 하는 핵심 항목이다.

### 2.3 피크 선택

적응 임계를 쓴다. 고정 임계는 셈여림 변화에 바로 깨진다.

```
θ(n) = median(ODF[n-W … n+W]) · α + δ        W = 8 프레임, α = 1.6
```

`ODF(n)`이 국소 최대이고 `θ(n)`을 넘으면 온셋으로 판정한다.
최소 온셋 간격 50 ms를 두어 중복 검출을 막는다.

## 3. 템포 추정

### 3.1 주기성 분석

ODF 시계열에서 주기성을 찾는다. 분석 윈도우는 최근 6초.

콤 필터 뱅크를 쓴다. 후보 템포 40~208 BPM을 로그 간격으로 샘플링하고, 각 후보
주기 τ에 대해:

```
S(τ) = Σ_i ODF(n - i·τ) · w(i)        i = 0 … ⌊L/τ⌋,  w(i) = 감쇠 가중
```

`S(τ)`가 최대인 τ가 박 주기 후보다.

### 3.2 옥타브 오류 처리

주기성 분석은 실제 템포의 1/2배, 2배를 자주 고른다. 특히 피아노에서 8분음표가
연속되면 2배 템포로 잡힌다.

대응:
- 선호 곡선을 곱한다. 중심 100~120 BPM의 로그 정규 가중
- τ와 τ/2, 2τ의 점수를 비교해 비율이 임계 이내면 선호 곡선이 높은 쪽을 택한다
- **결정적 완화**: 사용자가 곡의 대략적 템포를 알고 있으면 지정하게 한다. 악보에
  이미 적혀 있는 경우가 많다(♩=120). 이 힌트 하나가 옥타브 오류를 거의 없앤다.

### 3.3 평활화

프레임마다 템포가 튀면 스크롤이 떤다. 추정 템포에 중위수 필터(최근 5개 추정값)
후 1차 저역 통과를 적용한다. 시간 상수 1.5초.

## 4. 정지 감지

`DESIGN.md` 2.3절의 요구사항을 구현한다. 드리프트 억제에도 가장 효과가 크다.

### 4.1 노이즈 플로어 추정

환경에 따라 절대 임계가 무의미하므로 플로어를 추정한다.

```
floor = percentile_10( RMS_100ms 값들, 최근 10초 )
```

### 4.2 판정

```
RMS_100ms(n) < floor · 10^(6/20)   가  300 ms 연속  →  정지
RMS_100ms(n) > floor · 10^(10/20)  가  80 ms 연속   →  재개
```

진입/해제 임계를 다르게 둔 히스테리시스다. 임계가 하나면 경계에서 스크롤이
켜졌다 꺼졌다 한다.

정지 상태에서는 위치 적분을 멈춘다. 템포 추정도 동결한다(무음 구간이 템포 추정을
오염시키지 않게).

## 5. 악보 기하 분석 (ScoreGeometry)

악보 임포트 시 1회 실행하고 결과를 캐시한다. 실시간 제약이 없으므로 충분히 정밀한
처리를 할 수 있다.

### 5.1 전처리

1. PDFKit으로 200 DPI 그레이스케일 렌더
2. 이진화 — Sauvola 적응 임계. 전역 임계는 스캔 악보의 음영·얼룩에 깨진다
3. 기울기 보정 — -5°~+5° 범위에서 수평 투영 프로파일의 분산을 최대화하는 각도를
   찾아 회전. 오선이 기울어 있으면 이후 투영 기반 검출이 모두 무너진다

### 5.2 오선 검출

오선은 페이지 폭 전체에 걸친 검은 수평선이다. 수평 투영 프로파일에서 뚜렷한
피크로 나타난다.

```
P(y) = Σ_x binary(x, y)
```

`P(y)`의 피크를 찾고, **5개씩 등간격으로 묶인** 그룹을 오선으로 판정한다.
오선 간격(staff space)은 피크 간 간격의 중위수로 구한다. 이 값이 이후 모든
길이 판정의 기준 단위가 된다.

### 5.3 대보표 짝짓기

피아노 악보는 두 오선이 하나의 시스템을 이룬다. 어느 두 오선이 한 쌍인지
판정해야 한다.

**간격 통계는 쓰지 않는다.** 처음에는 오선 간 수직 간격을 모아 "시스템 내부"와
"시스템 사이"로 이분하려 했다. 실측에서 무너진다.

Chopin Op.6-2 1페이지:

| 쌍 | 간격 (px) | 실제 |
|---|---|---|
| 0-1 | 123.2 | **시스템 내부** |
| 1-2 | 137.3 | 시스템 사이 |
| 2-3 | 86.6 | 시스템 내부 |
| 3-4 | 113.4 | 시스템 사이 |
| 4-5 | 85.1 | 시스템 내부 |

첫 시스템만 제목·나타냄말 때문에 내부 간격이 123.2로 넓어져, 시스템 사이 간격
(113.4~137.3)과 분포가 겹친다. 간격만 보면 첫 대보표가 둘로 쪼개진다.

**연결선을 본다.** 대보표를 대보표이게 하는 것은 시작부에서 두 오선을 잇는
수직선이다. 간접 지표가 아니라 정의 자체이므로 이쪽이 옳다.

오선 좌측 끝 부근(-2 ~ +3 오선간격)에서 두 오선 전체를 덮는 열의 최대 비율:

| | 비율 |
|---|---|
| 같은 시스템 | 1.004 ~ 1.005 |
| 다른 시스템 | 0.351 ~ 0.542 |

Bach BWV846, Chopin Op.6-2 양쪽에서 완전히 분리된다. 임계 0.85.

연결선을 직선으로 그리지 않고 중괄호만 쓰는 판본을 위해 간격 통계를 폴백으로
남겨둔다.

### 5.4 마디선 검출

각 시스템 안에서 열별 잉크를 세어 수직선을 찾는다. 임계를 어디에 두느냐가
문제인데, **시스템 전체 높이를 기준으로 삼으면 실패한다.**

| 악보 | 마디선 양식 | 시스템 높이 대비 |
|---|---|---|
| Bach BWV846 | 대보표를 관통 | 0.99 |
| Chopin Op.6-2 | 오선마다 끊김 | 0.575 |

조판 양식이 판본마다 다르다. 하나의 전역 임계로 두 양식을 가를 수 없다.
0.85로 두면 Chopin의 마디선을 전부 놓치고, 0.55로 낮추면 Bach에서 음표 기둥
(0.72)이 쏟아져 들어온다.

**오선별로 보면 두 양식이 같아진다.** 어느 양식이든 마디선은 각 오선을 위에서
아래까지 긋는다. 따라서 판별식은:

> 각 오선 안에서 오선 높이를 꽉 채우는 수직선이,
> 그 시스템의 **모든** 오선에 같은 x로 동시에 존재한다.

구현은 열마다 오선별 채움 비율을 구하고 그 **최솟값**을 본다. 임계 0.90.

겹세로줄·반복기호·종지선은 수직선 여러 개로 그려지므로 1.5 오선간격 이내면
하나로 합친다. 대표 위치는 두께 가중 평균으로 잡는다.

시스템 시작부의 연결선(5.3)은 이 판별식을 그대로 통과하므로 위치로 제외한다
(시작에서 2 오선간격 이내).

#### 알려진 한계 — 정렬된 음표 기둥

이 판별식도 **양손의 음표 기둥이 같은 x에 정렬되면** 마디선과 구별하지 못한다.
마주르카처럼 양손이 박에 맞춰 함께 치는 음악에서 실제로 발생한다.

국소 이미지 특징으로 분리를 시도했고, 전부 실패했다 (정답 57개 / 오검출 6개 실측):

| 시도한 특징 | 결과 |
|---|---|
| 오선 밖으로의 연장량 | 정답 최대 0.543 vs 오검출 최소 0.211 — 겹침 |
| 인접 열의 잉크량 | 정답 0.088 vs 오검출 0.070 — 사실상 동일 |
| 인접 열의 비오선 잉크 (음표 머리 유무) | 정답 57개 중 32개가 오검출 범위와 겹침 |

마지막 특징이 실패하는 이유는 단순하다. **마디선 바로 옆에 음표가 오는 것이
정상이다.** "붙어 있는 것이 없다"는 가정 자체가 성립하지 않는다.

이는 OMR에서 알려진 난제이며, 국소 특징으로는 풀리지 않는다. 설계상 함의는
`DESIGN.md` 6절에 적었다 — **매핑의 1차 단위를 마디가 아니라 시스템으로 둔다.**
시스템 검출은 두 악보에서 100% 정확했고, 마디는 그 안의 보조 눈금으로 쓴다.
등급 A(MusicXML/MIDI)에서는 이 문제가 아예 없다.
### 5.5 출력

```cpp
namespace nota {
struct Measure {
    int   index;          // 곡 전체에서의 마디 번호
    int   page_index;
    float canvas_y_top;   // 이어붙인 캔버스 좌표계
    float canvas_y_bottom;
    float x_start;
    float x_end;
    float ink_density;    // 오선 제거 후 잉크 픽셀 수 — 음표 수의 근사
};
}  // namespace nota
```

`inkDensity`는 6.2절의 재동기화에 쓰인다. 음표를 인식하지 않고도 "이 마디에 음이
많은가 적은가"를 알 수 있는 값싼 대리 지표다.

### 5.6 실패 처리

오선 검출 수가 비정상(페이지당 0개, 또는 간격 분산이 과대)이면 CV 결과를 폐기하고
사용자 캘리브레이션(등급 C)으로 전환한다. 틀린 매핑으로 스크롤하는 것보다 수동이
낫다.

## 6. 위치 추정 (PositionEstimator)

### 6.1 상태와 적분

상태는 악보상 위치 `p`(박 단위)와 템포 `T`(BPM)다.

```
연주 중:   p ← p + (T / 60) · Δt
정지 중:   p 유지
```

마디 → 박 변환은 박자표에서 얻는다 (4/4 → 마디당 4박).

### 6.2 재동기화

적분만으로는 드리프트가 누적된다(`DESIGN.md` 6절). 주기적으로 독립 추정을 수행해
보정한다.

**등급 B (PDF + CV)** — 온셋 밀도 매칭

최근 2초간 검출된 온셋 수를 세고, 현재 추정 위치 주변의 마디들의 `inkDensity`에서
기대되는 온셋 수와 비교한다. 추정 위치를 ±2마디 범위에서 이동시키며 가장 잘 맞는
위치를 찾는다.

```
p* = argmin_{p' ∈ [p-2마디, p+2마디]}  | observedOnsets(2s) - expectedOnsets(p', 2s) |
```

보정은 급격히 적용하지 않는다. 신뢰도에 따라 가중 혼합한다:

```
p ← (1 - β) · p + β · p*        β = 0.15, 매치 신뢰도에 비례
```

이는 상보 필터다. 적분은 단기적으로 정확하고 장기적으로 드리프트하며, 밀도 매칭은
단기적으로 거칠고 장기적으로 안정하다. 둘을 혼합한다.

**등급 A (MusicXML/MIDI 있음)** — 크로마 매칭

악보에서 기대 크로마 벡터를 합성하고, 관측 크로마와 온라인 DTW로 정렬한다.
밀도 매칭보다 훨씬 정확하다. 구현은 3단계로 미룬다.

### 6.3 급변 억제

재동기화 결과가 현재 위치에서 한 시스템 이상 떨어져 있으면 즉시 적용하지 않는다.
연속 3회 같은 방향으로 일관되게 나타날 때만 점프를 허용한다. 단발 오추정이 악보를
날려버리는 것을 막는다.

## 7. 스크롤 제어 (ScrollController)

위치 `p`를 화면 오프셋으로 바꾼다. 여기서 중요한 건 정확성보다 **부드러움**이다.
떨리거나 급변하는 스크롤은 추적 오차보다 연주를 더 방해한다.

### 7.1 목표 오프셋

```
y_target = geometry.canvasY(p) - readLineOffset
```

`readLineOffset`은 화면 높이의 1/3 (사용자 조절 가능).

### 7.2 임계 감쇠 스프링

목표를 그대로 따르면 재동기화 때마다 튄다. 2차 시스템으로 평활화한다.

```
ÿ = -2ζω · (ẏ - v_ff) - ω² · (y - y_target)
```

- `ζ = 1` — 임계 감쇠. 오버슈트 없이 가장 빠르게 수렴한다. 악보가 지나쳤다
  되돌아오면 연주자가 혼란스럽다
- `ω = 2π · 0.8 rad/s` — 시정수 약 0.2초. 측정 후 조정
- `v_ff` — 속도 피드포워드

### 7.3 속도 피드포워드

스프링만 쓰면 등속 구간에서 항상 뒤처진다(정상상태 오차). 기대 속도를 미리 넣는다.

```
v_ff = (T / 60) · (dy / dbeat)
```

`dy/dbeat`는 현재 시스템의 마디 높이 / 마디당 박수. 시스템마다 다르므로
`ScoreGeometry`에서 조회한다.

이 항이 있으면 스프링은 오차 보정만 담당하고, 기본 전진은 피드포워드가 맡는다.

### 7.4 속도 제한

```
|ẏ| ≤ v_max        v_max = 화면 높이 · 1.5 / 초
```

템포 오추정이나 재동기화 점프가 화면을 날려버리지 않게 한다.

### 7.5 수동 개입

사용자 터치 감지 시:
1. 스프링 즉시 비활성화, 제어를 사용자에게 넘김
2. 손을 뗀 후 300 ms 대기
3. 최종 오프셋을 `geometry` 역변환으로 `p`에 반영 — 즉 사용자가 스크롤한 위치를
   새로운 현재 위치로 받아들인다
4. 적분 재개

## 8. 0단계 검증 항목

`core/`와 `tools/`를 Linux에서 빌드해 확인한다. Xcode도 Android Studio도 필요
없다(`DESIGN.md` 9.3절). 검증에 쓰는 코드가 곧 배포되는 코드다.

각 항목은 통과/실패가 명확해야 한다.

| 번호 | 항목 | 통과 기준 |
|---|---|---|
| V1 | 오선·시스템 검출 | 악보 표본 20종에서 시스템 검출률 95% 이상 |
| V2 | 마디선 검출 | 같은 표본에서 마디 경계 오차 ±1 이내 90% 이상 |
| V3 | 온셋 검출 (페달 없음) | F-measure 0.85 이상 |
| V4 | 온셋 검출 (페달 사용) | F-measure 0.70 이상 — 실측으로 현실적 목표 재설정 |
| V5 | 템포 추정 | 메트로놈 연주에서 오차 2% 이내, 옥타브 오류 없음 |
| V6 | 위치 추정 드리프트 | 3분 연주 후 오차 1시스템 이내 |
| V7 | 정지·재개 | 연주 중단 500 ms 이내 스크롤 정지 |

V6이 가장 중요하다. 이것이 실패하면 설계를 재검토해야 한다.

### 8.0 V1 / V2 측정 결과 (2026-11-04)

실제 피아노 작품을 Verovio로 조판해 측정했다. 정답은 Verovio SVG의 오선·마디선
요소에서 직접 추출하므로 수작업 라벨링이 없다. 재현: `prototype/make_fixtures.py`
→ `prototype/evaluate_page.py`.

| 악보 | 시스템 | 오선 묶음 | 마디 | 정밀도 | 재현율 | F |
|---|---|---|---|---|---|---|
| Bach BWV846 | 7 / 7 | 14 / 14 | 21 / 21 | 1.000 | 1.000 | **1.000** |
| Chopin Op.6-2 | 6 / 6 | 12 / 12 | 36 / 42 | 0.857 | 1.000 | **0.923** |

- **V1 통과.** 오선과 시스템은 두 악보에서 하나도 틀리지 않았다.
- **V2 통과** (기준 F ≥ 0.90). 마디 경계 위치 오차는 평균 0.44 px.
- **재현율이 양쪽 모두 1.000이다.** 놓친 마디선이 없다. 오차는 전부 과검출이며,
  정체는 5.4절의 정렬된 음표 기둥이다.

표본이 2곡이고 모두 디지털 조판이라는 한계가 있다. 스캔본·사진본, 그리고 더
다양한 양식(반복 구간, 변박, 성부 분리)으로 넓혀야 한다.

### 8.1 Android 기기 검증 (3단계)

V3~V7은 iOS 마이크 기준으로 먼저 확정한다. Android는 하드웨어 편차가 크므로
이식 단계에서 별도 검증이 필요하다.

| 번호 | 항목 | 통과 기준 |
|---|---|---|
| A1 | `UNPROCESSED` 소스 지원 조사 | 대상 기기군에서 지원 비율 파악 |
| A2 | 폴백 경로(`VOICE_RECOGNITION`) 온셋 검출 | V3 대비 F-measure 하락 0.10 이내 |
| A3 | 입력 레이턴시 | Oboe 왕복 측정, 스크롤 반응에 영향 없는 수준 |
| A4 | 저가 기기 CPU 부하 | 분석 파이프라인이 실시간 대비 0.5배 이내 |

A2가 실패하는 기기군은 최소 사양에서 제외하거나, 해당 기기에서 적응 임계
파라미터를 별도로 조정한다.

이 항목들은 실기기가 필요하므로 0단계에서 수행하지 않는다.
